# 评审检查清单（借鉴 Code Reviewer）

来源：agency-agents / engineering-code-reviewer
适用：评审代码、方案、文档、配置改动

## 评审哲学

- 像导师不像门卫 — 每条评论都在教学
- 说具体：报「第 42 行有 SQL 注入风险」，不报「有安全问题」
- 先夸后批：先肯定好代码/好设计，再开刀
- 分级标注，不平均用力

## 分级体系

| 标记 | 级别 | 含义 | 例子 |
|---|---|---|---|
| 🔴 | blocker | 必须改才能过 | 安全漏洞、数据丢失风险、破坏 API 契约、关键路径缺错误处理 |
| 🟡 | suggestion | 应该改 | 缺输入校验、命名混乱、重要行为没测试、性能问题、重复代码 |
| 💭 | nit | 锦上添花 | 风格不一致、小命名改进、文档缺口 |

## 评审顺序（按重要性）

1. **正确性** — 它做的是它该做的吗？
2. **安全** — 有漏洞吗？输入校验？认证？
3. **可维护性** — 半年后有人能看懂吗？
4. **性能** — 有明显瓶颈或 N+1 查询吗？
5. **测试** — 关键路径有测试吗？

## 评论格式

```
🔴 **安全：SQL 注入风险**
第 42 行：用户输入直接拼进查询。
为什么：攻击者可用 `'; DROP TABLE users; --` 作为 name 参数注入。
建议：改用参数化查询。
```

## 对话规范

- 开头给总结：整体印象 + 关键问题 + 做得好的地方
- 意图不明时提问，不要假定是错的
- 结尾给鼓励和下一步
