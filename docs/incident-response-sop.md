# 事故应急 SOP（借鉴 Incident Response Commander）

来源：agency-agents / engineering-incident-response-commander
适用：自家生态（首尔网关 / 搬瓦工 / 任一节点失联或异常时）

## 核心原则

1. **先止血，后找根因** — 恢复优先，根因分析放后面
2. **无指责复盘** — 不问「谁搞的」，问「系统为什么允许这种失败」
3. **分级定节奏** — 严重度决定响应速度、汇报频率、升级路径
4. **实时记录** — 动作和时间线当场记，别靠记忆

## 严重度分级

| 级别 | 场景 | 响应 | 汇报节奏 |
|---|---|---|---|
| SEV1 | 全服务宕机 / 数据丢失风险 / 安全入侵 | <5 分钟 | 每 15 分钟 |
| SEV2 | 主要功能挂 / 25%+ 用户受影响 | <15 分钟 | 每 30 分钟 |
| SEV3 | 小功能坏 / 有临时方案 | <1 小时 | 每 2 小时 |
| SEV4 | 无影响 / 技术债 | 下一工作日 | 日报 |

**升级触发**：影响范围翻倍升一级；SEV1 无根因超 30 分钟 / SEV2 超 2 小时 → 升级；任何数据完整性疑虑 → 直接 SEV1。

## 响应流程

### Step 1 确认与宣告
- 验证是真故障还是误报（探测脚本先跑）
- 定级 → 宣告：「SEV2 已确认，我当指挥官，先看 X」

### Step 2 结构化排查
- **时间盒**：每个假设最多 15 分钟，不确认就换下一个
- 固定动作：hostname/uptime/负载 → 内存/磁盘 → 日志尾部 → 端口/服务状态
- 记录：动作 + 时间戳 + 结果

### Step 3 恢复与验证
- 先恢复（重启/回滚/切换），根因后查
- 用指标确认恢复，不是「看起来好了」
- 恢复后观察 15~30 分钟再宣布解决

### Step 4 复盘（48 小时内）
- 时间线过一遍，找系统性原因（5 Whys）
- 输出行动项：负责人 + 截止日期，跟踪到完成
- 沉淀进 runbook：下次同类故障直接照做

## 汇报模板

```
[SEV2] 首尔网关异常 — 状态：排查中
影响：飞书消息无法回复
现状：已排除网络，正在查进程
动作：探测脚本 scan.js 已跑，日志尾部见 XX
下次更新：15 分钟内
```
