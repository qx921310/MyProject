# 提示词工程规范（借鉴 Prompt Engineer）

来源：agency-agents / engineering-prompt-engineer
适用：设计/优化系统提示词、人设、工作指令

## 核心理念

提示词不是随口一句话，是**人和模型之间的契约**。
先定输出格式和成功标准，再写内容。

## 硬规则

1. **先定义成功标准** — 期望输出格式（JSON/Markdown/纯文本）、长度、语气，先写清楚
2. **版本化** — 提示词当代码管：v1/v2 + changelog，改动可追溯
3. **在真实环境测试** — 用实际要用的模型和参数跑，不同模型行为差异大
4. **不用模糊词** — 禁止「be helpful」「be concise」；要写「2 句话以内」「只输出 JSON」
5. **显式约束优于隐式期待** — 模型会填满模糊，模糊即风险
6. **每条提示词 ≥3 个测试用例** — happy path / 边界 / 失败模式

## 系统提示词模板

```markdown
## 角色
你是 [具体角色]。唯一职责是 [主任务]。

## 约束
- 输出格式：[JSON / Markdown / 纯文本 — 明确指定]
- 长度：[最多 N token / 句子 / 要点]
- 语气：[专业 / 轻松 / 技术] — 避免 [要排除的词]
- 范围：只处理 [主题域]。超出范围回复：「[兜底话术]」

## 推理
回答前在 <thinking> 标签内逐步思考，最终答案放 <answer> 标签。

## 示例
<example>输入: [真实用户消息] 输出: [期望输出]</example>
<example>输入: [边界输入] 输出: [边界期望输出]</example>
```

## 测试用例清单

| 类型 | 例子 |
|---|---|
| happy path | 正常问题 → 正常回答 |
| 边界 | 空输入、超长输入、非预期语言 |
| 失败模式 | 提示注入、越权请求 → 优雅拒绝 |

## 与 STYLE.md 的关系

- STYLE.md 是「人设」（我是谁）
- 本规范是「方法」（怎么设计/验证任何提示词，包括未来新角色）
- 新角色/新技能上线前，按本规范跑一遍测试用例
